# Manual Email-Importance Dataset and ML Guide

## 1. Purpose

This directory contains manually labeled email examples for a future
personalized model that predicts whether an email is important to the account
owner. The labels are personal preferences, not general-purpose judgments
about whether an email is important to other people.

The app records examples only after a message has been opened and its complete
RFC822 message has been fetched. The user explicitly chooses **Mark Important**
or **Mark Not Important**. No model training or prediction is currently
performed by the app.

## 2. Files

| File | Purpose |
| --- | --- |
| `manual_classification.jsonl` | Append-only collection of manually labeled examples generated by the app. |
| `DATASET_SPEC.md` | This format, preparation, training, and evaluation guide. |
| `demo_dataset.py` | Local inspection and educational Naive Bayes demo for the JSONL dataset. |

The data file is Git-ignored because it contains private email. Keep it on a
trusted device, do not upload it to a public repository or hosted notebook, and
make backups only in a location you trust. The app writes this directory beside
the source checkout or beside the frozen executable.

## 3. Current record format

`manual_classification.jsonl` is JSON Lines: each non-empty line is one
independent JSON object. New labels are appended; prior records are not updated
or removed. A record currently has this shape:

```json
{
  "recorded_at": "2026-10-05T20:30:00+00:00",
  "mailbox": "INBOX",
  "message_id": "12345",
  "classification": "important",
  "raw_email_encoding": "base64",
  "raw_email": "RnJvbTogLi4u"
}
```

| Field | Meaning |
| --- | --- |
| `recorded_at` | UTC timestamp when the label was recorded, in ISO 8601 format. |
| `mailbox` | Mailbox selected when the message was fetched. |
| `message_id` | IMAP message sequence identifier returned by the server. It is useful for provenance, but is not a stable cross-session identity. |
| `classification` | Label selected by the user: `important` or `not_important`. |
| `raw_email_encoding` | Currently always `base64`. |
| `raw_email` | Base64 of the exact bytes returned for the message by IMAP `FETCH (RFC822)`. |

Decode `raw_email` to recover the original RFC822 byte sequence; do not treat
the JSON string as the email body, and do not decode/re-encode the message
before preserving it. RFC822 data includes headers and MIME parts, potentially
including attachments. It may contain secrets, personal data, tracking links,
or malicious content. A decoded message is data, not something to render in a
browser, execute, or open attachments from automatically.

## 4. Loading examples

Read the file one line at a time so the dataset can grow without loading all
raw messages into memory. Validate each record before using it:

1. Parse the line as JSON; report malformed lines rather than silently skipping
   them.
2. Require a known `classification` value and
   `raw_email_encoding == "base64"`.
3. Base64-decode `raw_email` with strict validation.
4. Parse the decoded bytes using Python's email parser, for example
   `email.parser.BytesParser(policy=email.policy.default).parsebytes(raw)`.
5. Extract model features from parsed headers and text parts; keep the original
   decoded bytes unchanged as the source record.

Minimal loading example:

```python
import base64
import json
from email import policy
from email.parser import BytesParser

ALLOWED_LABELS = {"important", "not_important"}

def load_examples(path):
    with open(path, encoding="utf-8") as dataset:
        for line_number, line in enumerate(dataset, start=1):
            if not line.strip():
                continue
            record = json.loads(line)
            if record.get("classification") not in ALLOWED_LABELS:
                raise ValueError(f"Unknown label on line {line_number}")
            if record.get("raw_email_encoding") != "base64":
                raise ValueError(f"Unknown raw email encoding on line {line_number}")
            raw = base64.b64decode(record["raw_email"], validate=True)
            message = BytesParser(policy=policy.default).parsebytes(raw)
            yield record, message
```

Do not copy `message_id` as the training identity. IMAP sequence numbers can
change as messages are removed or a mailbox is reorganized.

### Run the local parser and ML demo

From the repository root, run:

```bash
python imp_classification_model/demo_dataset.py
```

The script validates every JSONL line, strictly Base64-decodes the raw message,
parses MIME with Python's standard email parser, displays message metadata and
extracted text, then fits a small multinomial Naive Bayes classifier using the
standard library. By default it displays the full extracted text body; treat
the terminal output as sensitive. To show only a short body preview, run:

```bash
python imp_classification_model/demo_dataset.py --summary
```

This classifier is an educational end-to-end check, not the recommended
production model. Its predictions are made on the same records used to fit it,
so they are not test accuracy and do not measure generalization. The script
warns when the dataset is small. In particular, the current small collection
can prove that the saved email can be decoded, parsed, converted into text
features, and accepted by a trainable classifier; it cannot yet prove that
predictions will be useful on future mail.

## 5. Preparing model examples

### 5.1 Define a consistent feature policy

Start with features that are available at prediction time and that reflect
personal importance:

- Subject text.
- Sender address and optionally sender display name.
- Plain-text body, with quoted reply history and signatures considered
  separately.
- Recipient relationship, such as whether the account owner is in `To` or
  `Cc`, if useful and handled privately.
- Simple metadata such as message age or whether the message is a reply, if
  these will be available in the running app.

Treat HTML as a source to extract text from, not as trusted content. Prefer
`text/plain`; if only HTML is available, strip markup with a well-tested parser.
Exclude attachment contents initially. Remove or normalize volatile material
such as long quoted threads, signatures, tracking URLs, and generated
disclaimers only after checking that those signals are not meaningful for the
user. Do not fetch remote images, follow links, or execute embedded content.

Avoid training on fields that reveal the answer through collection artifacts:
the `classification` label, `recorded_at`, file order, label-button state, or
message storage path. Usually exclude `mailbox` too, unless folder membership
will be a legitimate feature at prediction time.

### 5.2 Handle repeated and conflicting labels

Every button press creates a new row, even for an email previously labeled.
Thus, records are not guaranteed to be unique and the same email can have
multiple or even conflicting labels.

Before training:

1. Compute a SHA-256 fingerprint of the decoded raw bytes to identify exact
   duplicate messages. This fingerprint is for local deduplication; do not add
   it to the app's stored record unless the data schema is deliberately
   versioned.
2. Group exact duplicates so copies cannot land in both training and test
   sets.
3. Inspect groups with both labels. Resolve them deliberately (for example,
   ask the user to re-label, prefer an explicitly defined latest-label rule,
   or exclude unresolved groups). Do not silently count contradictory copies
   as separate independent examples.
4. Consider grouping related messages in the same thread together, to reduce
   near-duplicate leakage across splits.

If implementing a “latest label wins” rule, compare parsed `recorded_at`
timestamps within each duplicate group, document that policy, and retain the
original JSONL unchanged.

### 5.3 Class balance and quality

Count examples per label and inspect the data before fitting a model. A large
class imbalance can make accuracy misleading. Labels are subjective and early
examples may be inconsistent; inspect borderline cases and collect examples
from different senders, topics, and time periods. Do not manufacture labels or
assume that unlabeled mail is `not_important`.

## 6. Recommended learning path

### Stage A: Classical baseline

For a small personal dataset, begin with a simple, inspectable baseline:

- Combine subject and extracted body text.
- Use word and/or character TF-IDF features.
- Fit a regularized logistic regression or linear support-vector classifier.
- Encode labels consistently, for example `important` as positive class `1`
  and `not_important` as class `0`.
- Establish a majority-class baseline before interpreting model performance.

Classical models often work better than a neural network when there are only a
small number of labeled examples. They train quickly on a CPU and make it
easier to spot accidental leakage and overfitting.

### Stage B: Deep learning, only when justified

Consider a pretrained text encoder or fine-tuned transformer only after there
are enough diverse, reasonably consistent labels and a sound evaluation split.
Email bodies can be long: define a documented truncation or chunking strategy
and avoid letting quoted copies of the same thread leak across splits. A
pretrained model may require downloading model weights; keep raw email and
inference local unless there is explicit informed consent to use an external
service. Start with an existing local model rather than training a neural
network from scratch.

Deep learning is not automatically better for this task. Compare it against
the classical baseline on the same held-out groups and with the same feature
policy.

## 7. Train/validation/test design

Do not randomly split individual JSONL lines: duplicate button presses or
related thread messages could otherwise appear in both train and test data,
making results look artificially good.

Preferred evaluation for a growing personal dataset:

1. Group exact duplicates (and, where practical, conversation threads).
2. Sort groups by `recorded_at`.
3. Use older groups for training, the next time period for validation, and the
   newest period for final testing.
4. Keep all members of a group in only one partition.
5. Fit text vectorizers and other preprocessing using the training partition
   only; apply the fitted transform to validation and test data.

With very little data, report that the evaluation is highly uncertain. Use
grouped cross-validation for model selection where feasible, but preserve a
final time-based holdout if enough data exists. Never tune repeatedly against
the final test set.

## 8. Metrics and deployment threshold

Report at minimum the confusion matrix, precision, recall, F1 for the
`important` class, and the number of examples in each class and split.
Accuracy alone is not sufficient, especially if most messages have one label.

If a model outputs probabilities, inspect calibration and choose the threshold
based on the intended UX. A high-precision threshold is appropriate if false
“important” predictions are disruptive; a high-recall threshold is appropriate
if missing an important message is the greater cost. Keep manual labeling
available so predictions can be corrected and new training data collected.
Do not present uncertain predictions as authoritative.

## 9. Privacy, security, and retention

- The raw message is highly sensitive and may include the complete message
  body, recipient addresses, and attachments.
- Keep the dataset local and private. The repository ignores the generated
  JSONL file, but verify `git status` before committing or sharing an archive.
- Do not paste records into public issue trackers, online notebooks, or
  third-party model APIs.
- Limit access to backups and any derived feature files. Derived text remains
  sensitive even after Base64 decoding or vectorization.
- Decide on a retention/deletion policy before collecting a large dataset.
  Deleting a message from the source mailbox does not currently delete its
  saved training example.
- Parse email defensively. Never load or execute message-provided scripts,
  links, attachments, or serialized Python objects as part of preprocessing.

## 10. Dataset limitations and future improvements

- This is a single user's subjective binary classification task; it should not
  be interpreted as a general email importance dataset.
- Each click appends a new row, with no deduplication, correction, deletion, or
  model metadata in the app.
- `message_id` is an IMAP sequence identifier and can be reused or change; use
  decoded content fingerprints and thread grouping in offline tooling.
- App versions do not currently write an explicit schema version. If the
  record format changes, version it (for example, add a `schema_version`
  field) and make readers handle old and new records explicitly.
- RFC822 bytes are stored as Base64, which preserves them but increases file
  size by roughly one third. Attachments can make the data grow quickly.
- There is no automated model validation, prediction UI, or retraining
  workflow yet.

When building those features, keep the raw append-only collection as the
source-of-truth and write derived datasets, fitted preprocessors, and model
artifacts to separate, clearly named files. Record the feature policy,
deduplication and conflict-resolution rules, split dates, model version, and
metrics alongside each trained model so results can be reproduced without
modifying the original labels.
